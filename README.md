# BigPixels 放大台

基于开源 ONNX 权重实现的本地 AI 图像超分工具，目标是在自己的机器上复现 bigjpg 的“AI 无损放大”效果。
使用真实模型推理，不是演示代码。

```
低分图 ──双三次上采样 / 分块──> 深度卷积网络预测修正 ──> 高清大图
```

**图片不离开本机**：无上传、无任务队列、无调用额度。网页版本质上是一个本地服务，关闭窗口即结束。

## 快速开始

### 方式一：使用打包版本（推荐）

从 [Releases](../../releases) 下载最新压缩包，解压到任意目录（路径含中文亦可），然后：

| 系统 | 操作 |
|---|---|
| Windows | 双击 `start_web.bat` |
| macOS / Linux | `chmod +x start_web.sh && ./start_web.sh` |

启动脚本自动完成四步：

```
查找 Python  →  准备运行环境  →  自检 15 个权重，缺失则下载  →  启动服务并打开浏览器
```

首次运行较慢（需下载约 292 MB 权重并安装数百 MB 依赖），之后启动很快。
任何一步失败都会**停在该步并输出原因与后续操作**，不会一闪而过 —— 双击启动的窗口在脚本结束后即关闭，不做暂停则看不到输出。

> **权重为什么不随压缩包分发？**
> 权重合计约 292 MB，单文件超过 100 MB 即被 GitHub 拒绝；每次修改代码都重传权重也不合理。
> 因此仓库只保留一份清单（文件名 + **精确到字节**的大小），权重按需下载。
>
> - 默认使用国内镜像 **hf-mirror.com**；配置代理后可用 `--source hf` 切回官方源。
> - 中断后重新运行即可**断点续传**（进度记录在 `.part`），已完成的部分不会重复下载。
> - 下载完成后会**再自检一次**才判定成功 —— 判据是字节数完全一致，因此“文件存在”等价于“文件完整”。
> - 半截文件、git-lfs 指针、下载站返回的 HTML 错误页都会被识别并重新下载，
>   不会留到几分钟后由 onnxruntime 抛出难以理解的异常。

### 方式二：手动安装

```bash
# 需要 Python 3.9 以上
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # Windows
.venv/bin/python    -m pip install -r requirements.txt    # macOS / Linux

python tools/download_models.py        # 下载权重（约 292 MB，走 hf-mirror）
python tools/upscale.py 图片.jpg -o 输出.png --preset art --scale 4    # 命令行单张

python app/server/bootstrap.py          # 上述流程的编排：环境 → 模型 → 启动服务
python app/server/bootstrap.py --check  # 仅自检（环境 + 模型），不安装、不下载、不启动服务
```

网页版默认地址为 http://127.0.0.1:8765（更换端口：`--port 8766`，或修改 `start_web.bat` 首行）。

**服务默认绑定所有网卡**，因此同一 Wi-Fi 下的手机、平板也可访问 —— 启动时会同时输出可用的局域网地址
（`同一个 Wi-Fi 下也能开： http://192.168.x.x:8765/`）。
若不需要同网络内其他设备访问，请加 `--host 127.0.0.1`（该界面没有访问控制，任何能打开它的人都可以读写 `outputs/`）。

> **绑定地址与可访问地址的区别**
>
> `0.0.0.0` 是绑定用的通配地址，含义为“接收所有网卡的连接”，它本身**并不是可连接的目的地址**。
> 早期版本把它直接拼接成 `http://0.0.0.0:8765` 输出并交给浏览器打开，结果是服务运行正常、浏览器提示
> “无法访问此页面”（Chrome 报 `ERR_ADDRESS_INVALID`），与端口配置无关。
> 现在“绑定地址”与“可访问地址”分开计算，`smoke.py` 中也有对应断言。

模型不完整时**无需核对文件名**：启动时逐个自检并列出缺失项；页面顶部同时给出提示，并把预设自动切换到可用的一档。
（命令行可用 `tools/upscale.py --info` 查看权重清单。）

## 命令一览

命令行入口全部位于 `tools/` 下（均为薄壳，见「目录」一节）。

```bat
:: 二次元插画 4 倍（anime 即默认值，可省略）
.venv\Scripts\python.exe tools\upscale.py in.png -o out.png --preset anime --scale 4

:: 更接近线上观感：加 --clear crisp 与 --bright lift
.venv\Scripts\python.exe tools\upscale.py in.png -o out.png --preset anime --scale 4 --clear crisp --bright lift

:: 卡通 / 插画使用轻量模型（waifu2x，2× 串联两次，仅 CPU，细节较少）
.venv\Scripts\python.exe tools\upscale.py in.png -o out.png --preset art --denoise medium --scale 4

:: 整个目录批量处理
.venv\Scripts\python.exe tools\upscale.py D:\pics -o D:\out --preset esrgan --scale 4

:: 同时输出一张双三次插值对照图
.venv\Scripts\python.exe tools\upscale.py in.png --compare

:: 查看设备与模型状态 / 列出预设
.venv\Scripts\python.exe tools\upscale.py --info
.venv\Scripts\python.exe tools\upscale.py --list
```

| 参数 | 取值 | 说明 |
|---|---|---|
| `--preset` | `anime` / `art` / `art-hd` / `esrgan` / `photo` | 图片类型，决定使用哪一族权重。**二次元插画应选 `anime`**（见下文） |
| `--scale` | `2` `4` `8` `16` | 目标倍率，不足或超出部分由网络串联 + Lanczos 收尾补齐 |
| `--denoise` | `none` `low` `medium` `high` `highest` | 降噪档，本质是不同训练噪声水平的权重。仅 waifu2x 系（`art` / `art-hd` / `photo`）具备；`anime` / `esrgan` 忽略此项 |
| `--clear` | `soft` `normal` `crisp`，或直接给数字 | 收尾清晰度。网络输出的是渐变边缘，该档决定是否将其压回硬边（见下文） |
| `--bright` | `off` `lift`，或直接给数字 | 明暗。`off` 为默认值、最贴近原图；`lift` 整体 ×1.019，对应线上那种通透感（见下文） |
| `--tile` | 默认 256 | 瓦片边长，显存不足时调小 |
| `--device` | `auto` / `dml` / `cpu` | 推理后端 |

## 网页版（`web/`）

双击 `start_web.bat`，或执行 `.venv\Scripts\python.exe app\server\server.py --port 8765`，浏览器打开 http://127.0.0.1:8765。

页面分为三份：`web/index.html` 只保留骨架，版式在 `web/css/app.css`，行为在 `web/js/app.js`，
服务端按 `/css/` 与 `/js/` 两个前缀将其发出（后缀白名单与目录穿越拦截与 `/fonts/` 采用同一套实现）。
拆分的目的只是修改时不必在两千行中定位某段 `<script>`；**没有构建步骤**，修改后刷新页面即可生效
（这两个前缀刻意返回 `no-store`，避免浏览器缓存导致误判为修改无效）。

页面按 bigjpg 的思路设计，六步选完即可得到结果：

1. **选图** —— 拖入图片，或点击左侧示例（三张合成样图：线稿 / 小字截图 / 噪点照片）。
2. **这是什么图** —— 五个预设，各附一句说明，**默认落在“动漫插画”**（二次元图在此档细节保留最多）。
3. **放大多少倍** —— 2× / 4× / 8× / 16×，下方**实时计算输出尺寸**（`360 × 240 → 1,440 × 960`）。
4. **要不要降噪** —— 关 / 低 / 中 / 高 / 最高。
5. **线条要多清楚** —— 原样 / 标准 / 更锐。
6. **明暗** —— 原样 / 提亮。**一个开关，默认关闭**。

分块边长、推理后端、权重清单等配置全部收纳在“更多设置与引擎信息”中，不占用主界面。

**窄屏（≤700px）下这六步整块收进从底部拉起的抽屉，默认收起。** 手机屏幕高度有限，
主要观察对象是图片本身，不应被六个步骤长期占用。页面只保留一条动作栏：左侧显示“当前图片 +
当前参数”，右侧的“开始放大”即主按钮本身（其禁用状态与文案与抽屉内的按钮保持同步，
不会出现“动作栏为禁用态但实际可点击”的情况）。点击动作栏、点击遮罩、按 `Esc` 均可拉开或收起。

抽屉最高占 86% 屏高，上方始终保留一段光台 —— 以此表明这是“拉开一层”而非“切换页面”。
键盘焦点会随抽屉进入并限制在其中，否则 Tab 会移动到被遮罩覆盖的区域。
宽屏（>700px）行为不变，仍是左侧控制栏 + 右侧光台 / 放大镜。

### 为什么同样的图，本地会比 bigjpg 糊

**主因不是清晰度档，而是预设选择错误。** 这一半的责任在于原界面的排序：排在首位的
“卡通 / 插画”使用的是 waifu2x CUnet —— 它是 **2× 网络、4× 需串联两次**，
两次上采样本身就会丢失细节。真正为二次元插画准备的那一档（4x-AnimeSharp）原本排在最后，
名为“动漫线稿”、说明写着“线稿专用”，难以被联想到该选它。

以同一张 351×1295 的动漫插画、同样 4× 为例，取细节热点区（眼睛 + 发丝）的拉普拉斯方差与
线上 bigjpg 的 4x 卡通对比（后者记为 100%）：

| 预设 | 权重 | 达到 bigjpg 的比例 |
|---|---|---|
| **动漫插画（当前默认）** | 4x-AnimeSharp · **原生 4× 一次推理** | **107%** |
| 通用场景 | Real-ESRGAN x4plus · 原生 4× | 37% |
| 卡通 / 插画（轻量） | waifu2x CUnet · 2× **串联两次** | 35% |
| 插画 高清 | waifu2x Swin · 2× **串联两次** | 29% |

相差的这三倍**无法用锐化弥补**：把增益从 2 提到 6，锐度数值可达 2241（数值上高于 bigjpg 的 2007），
代价是局部对比度 62.9（bigjpg 为 41.3）、平块噪声 ×3 —— 这是把对比度与噪声一并抬高，而非恢复细节。
bigjpg 的特征是**在低得多的对比度下达到两倍锐度**（41.3 / 2007），这只有真实细节才能做到。

另外，这一档也更快：waifu2x 系在 DirectML 上数值错误、只能退回 CPU，而 4x-AnimeSharp 运行在 GPU 上。
**又快又锐，因此它成为默认值。**

那么**收尾锐化**（第 5 步“线条要多清楚”）解决的是什么问题？它针对的是另一件事：
网络输出的边缘天然是**渐变**的（1 px 的线摊成 4~7 px 灰带），这一步把边缘收回。
它只作用于边缘 —— 平坦区 32×32 块的 std 始终为 `0.00`，不会在干净区域产生噪点。
**原样**档即关闭该处理，与不做锐化逐像素一致；**更锐**档最接近线上观感。
但它无法恢复“模型本身未补出的细节”，那取决于上文那张表。

**一句话概括**：选对预设是主要因素（相差 3 倍），收尾锐化是次要调整（再收敛一点边缘）。

### 第 6 步“明暗”是什么，为什么默认关闭

线上 bigjpg 的输出看起来比原图“通透”一些。对同一张图的平坦区测量后确认，
它实际是**整体提亮**：亮部 +4.8 灰阶、中间调仅 +1.1 灰阶。
这一形状对应**乘法**（每个像素乘以一个略大于 1 的数），而非加常数 ——
加常数会把中间调一并抬高，并使纯黑发灰。三种拟合中乘法残差最小
（4.11 灰阶；加常数 4.30，提 gamma 5.88），拟合得到的增益为 **×1.0192**。

因此这一档即乘以 1.019，在“原样 / 提亮”之间切换：

| | 观感 | 对原图的保真度（PSNR，以用户提供的卡通图测量） |
|---|---|---|
| **原样（默认）** | 与原图亮度一致 | **32.99 dB** |
| **提亮** | 接近线上那种通透感 | 会下降 |

**它是唯一一个会降低指标的可选项，因此需要明确说明**：提亮以“输出更不像原图”为代价。
另外，即便开启提亮，本地对原图的保真度仍高于线上 bigjpg（30.38 dB）——
因为 bigjpg 那 +4 灰阶的提亮本身就是其对原图失真的主要来源之一。
追求“最还原”应保持原样，追求“最像线上”则开启提亮，这两个目标在此处相互冲突，
因此将其做成开关交由使用者决定，而不是替使用者修改默认值。

命令行对应 `--bright off|lift`（也可直接给出乘数，例如 `--bright 1.05`）。

出结果后：

- **对照台**：原图与结果叠在同一块深色光台上，拖动中间竖线左右对比（键盘左右键亦可）。
  点击“**全屏对比**”（或按 `F`）可将光台铺满整个屏幕，细节少一次缩放即少一次失真；
  全屏下 `← →` 微调分割线、`Esc` 退出。全屏时**右侧还挂有一栏实时细节对比** ——
  鼠标在左侧画面移动，右侧即显示光标处框选区域（复用同一套三格 DOM，不会重复请求）。
  光台上显示的是**缩略预览**（最长边 1600 px）—— 6744×10112 的原始 PNG 交由浏览器解码，仅这一步就会明显卡顿。
- **放大镜**：三格并排，位于右栏最前（**在“这次改了什么”折叠栏之前** —— 该折叠栏展开后有
  数十行计量表，放大镜排在其后容易被挤出屏幕）——
  原图像素块（最近邻）/ 双三次插值 / AI 结果，**锁定在同一块画面、同一个屏幕尺寸**上。
  倍率单位为“屏幕像素 : 输出像素”，**默认 1:4**：一格容纳四倍于格宽的画面，
  初始即可看清画面内容，而不是一格模糊的像素。如需观察模型的原始像素，按 **1:1**
  （该档下 AI 格即模型自身像素，判断“细节是真实恢复还是编造的”依据在此）。
  比 1:1 更远的档位（1:2 / 1:4 / 1:8）用于观察整体结构，最远档受单次取块边长上限约束，
  达不到时标签会显示实际可达倍率（窗口变窄时 `1:8` 可能显示为 `1:7`）—— 不会标注无法达到的数值。
  倍率有**两个入口，指向同一状态**：五个预设档用于一键跳转到固定刻度，下方的**取景滑块**
  用于连续调节。拖动滑块后各档位均不处于选中态（滑块位于两档之间），点击档位则滑块自动移动。
  滑块两端由当前图片实际可计算的范围决定，因此从最远到最近全程可拖动。
  三格不是把整幅图放入 `background` —— 那样鼠标每次移动都要重排一张 68 MP 的位图。
  此处采用**按需取块**：只向服务端请求当前查看的一小块真实像素。
  倍率比 1:1 更远时会把**屏幕尺寸**一并告知服务端（`dw`），由服务端先缩放再返回；
  缩略预览的分辨率足以支撑该格时直接从预览取用，不足则回到原像素拼合 —— 宁可慢一些，不模糊。
  光台上的十字框**左上角即放大镜当前查看区域的左上角**，鼠标推到画面边角时框也随之到边：
  视窗中心固定在鼠标位置、允许一角伸出图外（伸出部分由光台裁掉），
  而不是把视窗整体限制在图内 —— 限制在内时鼠标到边后框最多只能到达距边半格处，始终存在偏差。
  全屏时这套三格 DOM 会被移动至光台右侧一栏复用，同样**没有第二条取块通道**。
  两块**同屏**需要精确的高度预算：光台与放大镜各自都倾向变大，合并后即超过一屏，滚动则只剩其一。
  因此放大镜一出现，光台长边即从 `56dvh` 收到 `40dvh`、三格边长收到 `25dvh`
  （两者均由视口高度驱动，矮屏随之缩小），连“结果存哪了”那条提醒也从两块之间移到了左侧控制台。
  1920×1080 窗口下实测为 899 px / 982 px 视口，1600×900（vh≈802）同样可容纳；
  视口低于 800 px（笔记本横屏再叠加书签栏）才需要滚动。该约束由 `shots.py` 现场判定。
- **计量表**（折叠）：尺寸、模型、耗时、吞吐，以及三项直接计算的指标 —— 回环一致（结果缩回原尺寸后与原图的 SSIM / PSNR）、
  锐度增益（对双三次的拉普拉斯方差之比）、体积对比（同尺寸 PNG 大小）。

### 结果放哪：保存模式 / 暂存模式

**默认为保存模式**：每次任务对应一个文件夹，位于 `outputs/web/`，名称为 `<时间戳>_<图名>_<任务号>`：

```
outputs/web/20260920-191402_SharkGirl_843x1264_e3c72086d0a7/
    input.jpg            原图（后缀随上传）
    result.png           AI 放大结果（模型原生分辨率，无损）
    bicubic.png          双三次基线（输出大于 30 MP 时不再生成，以省去整幅编码）
    preview-input.png    最长边 1600 的缩略预览（光台使用）
    preview-result.png
    tiles/{input,result}/  1024² 瓦片（大于 4 MP 才切分，放大镜按需读取）
    job.json             该任务的完整记录（重启后 `?job=` 仍可识别）
```

保存模式下服务**不自动清理任何内容**。累积过多时自行删除该目录下的文件夹，或切换到下述模式。

在“更多设置与引擎信息 → 结果去向”中可切换到**暂存模式**：结果仅在服务运行期间保留，
超出条数 / 磁盘限制时按时间淘汰，**服务停止即清空整个工程目录** —— 因此出图后界面会即时提示
“这份结果不会留盘，先按下载存一份”。切换模式本身不删除任何内容，删除只发生在淘汰与退出时刻。

模式记录在 `outputs/settings.json`，重启后仍生效；启动时也可用 `--keep 1|0` 覆盖。

旧版本将产物直接铺在 `outputs/web/` 根目录下，多次运行后十分混乱。现在启动时会**自动归档**为上述结构：
按任务号归组、按时间戳命名、先把文件移动到新位置再删除旧文件，因此是无损且幂等的（第二次运行不会产生任何变动）。
归档时若发现某条旧结果连记录都不存在（早期版本不写 `job.json`），会为其补写一份：
能推导出的字段（尺寸、体积、倍率）补齐，无法推导的（耗时、锐度）留空由界面显示“—”，**不编造数值** ——
同时把该条 `?job=<id>` 链接恢复可用。

### 启动自检

`app/server/server.py` 启动时会逐项检查，缺失项直接列出：

```
BigPixels 本地版已启动： http://127.0.0.1:8765
  同一个 Wi-Fi 下也能开： http://192.168.1.23:8765
  （默认绑在所有网卡上，同一个网络里的人都能打开；只想自己用就加 --host 127.0.0.1）
模型自检：15/15 个权重都在  <解压目录>\models
设备自检：有缓存，直接按上次的结论跑
工程目录 <解压目录>\outputs\web  ·  已有 21 次工程  ·  ?job=<id> 的链接还能用
结果保存：保存模式 —— 出来的结果就留在上面那个文件夹里，不自动清理
按 Ctrl+C 停止
```

第一行是**本机**地址（双击启动时浏览器打开的就是它），第二行是**同一 Wi-Fi** 下可用的地址。
若端口上已有服务在运行（通常是上一次的窗口未关闭），会在最前面直接指出 ——
Windows 因 `SO_REUSEADDR` 的语义**允许第二个进程绑定同一端口**（Linux 会拒绝），
因此两个服务抢占同一端口时不会报错，请求只会发送到后启动的那个，容易造成“代码修改未生效”的误判。

权重不完整时会列出缺失项（文件名、当前字节数、应有字节数）。
双击启动路径会**自动下载**；单独运行 `app/server/server.py` 时则提示执行
`python tools/download_models.py`（走 hf-mirror 镜像；速度慢或连接失败可先配置代理再运行）。
页面同时显示提示，并自动把预设切换到可用的一档，避免点击后才发现缺少权重。

页面中的图片始终不离开本机。地址栏会带上任务号（`?job=<id>`），刷新不丢结果，也可把该链接直接发给他人；
`?demo=lineart` 可预载指定示例，`?theme=dark` 强制使用深色主题。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 页面 |
| GET | `/fonts/<file>`、`/demo/<file>` | 自托管字体与示例图（含路径穿越防护与后缀白名单） |
| GET | `/api/presets` | 预设、降噪档、倍率、分块档、示例图、模型自检、工程目录、磁盘占用、当前设置 |
| GET | `/api/settings` · POST `?keep=1\|0` | 读取 / 修改“保存 · 暂存” |
| POST | `/api/job?preset=&scale=&denoise=&clear=&bright=&tile=&name=` | 请求体为图片二进制，返回 `{id}` |
| GET | `/api/job/<id>` | 进度、阶段、耗时、指标、工程目录（`tiled` 指明哪几层已预切块） |
| GET | `/api/job/<id>/input` · `/baseline` · `/result` | 原图 / 双三次基线 / AI 结果（均为 PNG） |
| GET | `/api/job/<id>/result?view=1` | 缩略预览（最长边 1600 px），**光台只读取此项** |
| GET | `/api/job/<id>/detail?layer=&x=&y=&w=&h=&dw=` | 一小块真实像素，供放大镜使用。`layer` 取 `input` / `bicubic` / `result`；坐标按**输出像素**给出，由服务端换算。`dw` 表示“该块最终在屏幕上绘制的宽度” |
| DELETE | `/api/job/<id>` | 删除一次工程（记录与文件夹一并删除）。任务仍在运行返回 409 |

`/detail` 的三条约定：`input` 返回**原生输入像素**（客户端按比例放大并使用 `image-rendering:pixelated`，显示的才是真实像素块）；
`bicubic` 为**仅计算该小块**的双三次结果，因此输出达到 68 MP 时仍可对比 —— 整幅双三次落盘代价过高，仅在 ≤30 MP 时执行；
当 `dw` 小于取块边长时（即倍率比 1:1 更远的几档），服务端**先缩放到屏幕尺寸再返回**，
否则把一大块原像素传给浏览器缩放，会多传输数十倍字节并多解码一次。1:1 档下 `dw` 恰好等于边长，不做任何像素改动。

`app/qa/cdp.py` 是一个仅使用标准库实现的 Chrome DevTools 客户端。自行实现的原因是：该环境没有 websocket 库，

“界面是否搭建完整、是否存在静默报错”这类问题，比人工查看截图更可靠。

## 实测效果（`tools/bench.py`，160×120 → 640×480）

标尺为合成的高清原图，指标为与原图的 PSNR / SSIM。
下表由**当前代码**跑出（含默认的收尾锐化、明暗 `off`）；更换 `--clear` / `--bright` 后数值会变化。

| 样本 | 预设 | 降噪 | PSNR(双三次) | PSNR(AI) | SSIM(双三次) | SSIM(AI) |
|---|---|---|---|---|---|---|
| 卡通插画 | anime | 无 | 22.10 | **24.77** | 0.7896 | **0.9049** |
| 卡通插画 | art | 中 | 22.10 | **22.64** | 0.7896 | **0.8817** |
| 卡通插画 | art-hd | 中 | 22.10 | **23.14** | 0.7896 | **0.8722** |
| 卡通插画 | esrgan | 无 | 22.10 | **23.20** | 0.7896 | **0.8731** |
| 照片 | photo | 中 | 19.97 | 19.50 | 0.6380 | 0.6312 |
| 加噪照片 | photo | 无 | 18.88 | 17.50 | 0.3511 | 0.3570 |
| 加噪照片 | photo | 中 | 18.88 | **18.59** | 0.3511 | **0.5746** |
| 加噪照片 | photo | 最高 | 18.88 | **19.04** | 0.3511 | **0.6244** |

结论：

- **卡通 / 插画**：最优档（`anime`，即默认值）PSNR **+2.67 dB**、SSIM 0.79 → **0.90**，边缘由模糊变为锐利。
  waifu2x 两行（`art` / `art-hd`）仅 +0.5 ~ +1.0 dB —— 再次印证**2× 串联两次会损失细节**，
  选对预设比其他任何调整都重要。
- **加噪图**：降噪档主要作用于此类图，SSIM 0.35 → **0.62**，且档位单调
  （无 0.36 < 中 0.57 < 最高 0.62），说明 noise0~3 是真实生效的独立权重。
- **干净照片**：与双三次基本持平（略低）。原因是样本为 Lanczos 降采样生成的合成图，
  双三次本就能较好还原；真实场景中压缩痕迹较重的低分图收益会明显更大。
  这也是**为什么 `bench.py` 的门禁不为照片样本设阈值** —— 感知模型会“编造”纹理，以干净 GT 作为标尺只会频繁误报。
- 对比图位于 `outputs/bench/cmp_*.png`，左中右依次为：像素块原图 / 双三次 / AI。

## 实现要点与已知限制

以下 14 条是开发过程中定位并修复的问题记录。其中多数属于“不报错但结果不正确”的类型，
静态检查与常规截图测试都难以发现，特此记录以供后续维护参考。

**1. waifu2x 系模型的输出尺寸不是整数倍，需在运行时拟合。**
`Real-ESRGAN` 的输出为 `out = 4×in`；waifu2x 的两个网络内部会裁掉一圈边界：

```
Swin-UNet : out = 2×in − 32
CUnet     : out = 2×in − 72
```

硬编码尺寸必然错位。程序在加载模型时运行两次探针拟合出 `out = a×in + b`，据此决定外扩与裁剪量，并对结果做一次尺寸自检。

**2. DirectML 对部分模型会静默产生错误数值。**
尺寸正常、图像也能输出，但内容无效 —— waifu2x 系在 DML 上 PSNR 仅 1.98 dB，同一份代码在 CPU 上为 23.62 dB。因此加载时会用固定输入同时运行 GPU 与 CPU 并比对，偏差超过阈值即自动退回 CPU，结论缓存至 `models/.device_probe.json`。Real-ESRGAN 系在 DML 上结果正确，继续使用 GPU。

**3. hf-mirror 不接受开放区间的 Range 请求。**
`Range: bytes=0-` 返回 404，而 `bytes=0-4194303` 这类**有限区间**正常。因此 `download_models.py` 按 4 MB 分块下载并校验总大小，大文件才能完整获取。

**4. Google Fonts 的多字重请求会导致同一文件被重复写入。**
`family=Archivo:wght@600;700` 这类一次请求多个字重的写法，返回的 CSS 按**子集分组**（vietnamese / latin-ext / latin 各一段，
每段内再分字重），子集注释位于 `@font-face` **之前**。若解析时只匹配 `@font-face` 块、使子集名退化为默认值，
vietnamese / latin-ext 也会被当作 latin 收下，同一文件名被反复覆盖 —— 最终 `archivo-600.woff2` 与 `archivo-700.woff2`
字节完全相同。`app/tools/fetch_fonts.py` 改为**一个字重一次请求**，只取 `/* latin */` 段，抓取完成后再用 md5 去重校验。

另外，拉丁子集中不含 `→`(U+2192)，箭头会落到系统字体、与等宽数字无法对齐，因此单独抓取了一份符号子集（1.3 KB）。

**5. 一个 68 MP 的输出会在两处拖垮机器，且都不报错。**

第一处在服务端。指标中的“锐度增益”需要与双三次基线对比，原实现是**先把整幅图插值成双三次**再取中心 512×512 ——
6744×10112 转为 float32 是 **816 MB**，加上中间那次除以 255 又是 816 MB，峰值 1.56 GB，只为计算一个 0.5 MP 区域的方差。
现在先裁出源图的对应区域、只插值那一小块，峰值 6.7 MB，且结果**逐像素一致**（`app/qa/perf_probe.py` 中已核对）：

```
旧：整幅双三次插值     1.38 s   峰值 1560.9 MB
新：只插值中心那一块   0.01 s   峰值    6.7 MB     最大绝对差 0.000000
```

第二处在浏览器端。34.83 MB 的原尺寸 PNG 直接作为 `<img>` 显示，解码后是 272 MB 的位图；
放大镜再把同一张图作为三格 CSS `background`，鼠标每次移动都重设 `backgroundSize` —— 等于每帧重排一次 68 MP。
现在光台只加载**缩略预览**（1066×1600，1 MB），放大镜改为**按需取块**：大图在任务结束时预切成 1024² 的 PNG 瓦片，
取块时只读取命中的几块，一次几十毫秒、几十 KB。实测横扫对照台 48 次：长任务 0 个、帧间隔稳定 17 ms。

以上改动只涉及“怎么算、怎么传”，不影响输出本身：下载得到的始终是模型原生分辨率的无损 PNG。

**6. 异步取块完成后必须无条件重绘，否则首屏为空白。**

放大镜改为三格 `<img>` 之后，`drawLoupe()` 的入口是 `if (!S.view || !g) return;`。
首次取块时 `S.view` 仍为 `null`，该次 `drawLoupe()` 直接返回，`--tilew/--dx/--dy` 均未设置。
落地后原本只在“需要重新判定”时才补绘一次，于是**鼠标未移动时三格始终为黑**；手动移动鼠标后自行恢复。
这类“一动就好、不动就坏”的问题，靠鼠标驱动的截图脚本无法发现（每次截图前都会先 hover），
是通过 DOM 测量得出的：`--tilew` 为空字符串、`<img>` 实际尺寸为 0×0。
修法是落地后无条件再调用一次 `updateLoupe()`，同时移除了 `recheck` 这一中间状态。

**7. 全屏侧栏出现横向滚动条，原因是一行内联样式。**

放大镜倍率由三档增至五档后，全屏右栏在窄窗口 / 矮窗口下出现横向滚动条。
排查结果：栏宽足以容纳五个按钮，但 `#zoom` 上有一行 `style="flex:0 0 auto"` ——
**内联样式优先级高于所有样式表**，导致“允许折行”生效而“允许收缩”永远不生效，五个按钮被撑出栏外。
删除该内联样式、仅保留样式表规则后正常。
同时把 `--fspane` 的固定开销从“按一行标题计算”改为“按两行计算”：窗口变窄时倍率按钮会折行，
仍按一行计算高度会使三格被顶出。**这类仅在“窄窗口 + 字段数增加”时出现的问题，默认尺寸的截图无法发现，需指定其他尺寸重新测量。**

**8. 远倍率档不应从瓦片拼合大块像素。**

1:1 档需要真实像素，从 1024² 瓦片中按需读取几块即可。
而 1:4 / 1:8 需要把一大块画面压进一格：若同样走瓦片拼合，一次需拼合数千万像素（几十 MB、半秒以上），
而该画面最终只绘制到几百像素宽，拼出的绝大部分像素随即被丢弃。
缩略预览（最长边 1600）本身就是整幅图的一次性缩放，这一档从它取用，几十毫秒即可返回，
压缩到一格大小后在屏幕上无法分辨差异。**判断标准是“预览缩放后是否仍足以绘制这一格”**：
足够则走预览，不足（例如 68 MP 输出配 1600 的预览）则回到原像素路径 ——
宁可慢一些，也不让 AI 那一格比其他两格模糊。1:1 档的 `dw` 恰好等于取块边长，不做缩放，仍走原路径，逐像素不变。

**9. 十字框跟不上鼠标：视窗被限制在图内，且框按“中心”定位。**

用户反馈为“鼠标都到那个原图文字了，框框没到”“卡这里过不去了”。定位到两处：

其一，`loupeGeom()` 将视窗中心限制为 `clamp(鼠标位置, V/2, W−V/2)`，即视窗必须整体位于画面内。
于是鼠标推到边角时，视窗中心最多到达距边 `V/2` 处就被顶住。在 68 MP 的图上 `V/2 ÷ W ≈ 8%`：
**框与边缘始终相差 8%**，继续推动鼠标也不再变化。改为中心固定于鼠标位置、允许视窗伸出图外
（伸出部分由 `region()` 裁掉，取块只关心图内部分，光台显示的底色即图外留白）。

其二，十字框定位使用 `left: (cx/W)%`，即把**中心**当作左上角，导致整个框偏移半格，
所框区域与放大镜显示的不是同一块画面。改为 `left: (vx/W)%`。

两处单独修复都不充分，且**均不报错、静态截图也无法发现**（截图前都会先 hover 到画面中央，该位置偏差最小）。
现在由 `shots.py --probe` 中的 `probe_frame()` 覆盖：鼠标推到四条边与四个角，
逐项断言“框左上角 == 视窗左上角”以及“贴边时框确实到边”。
该探针在保留前已**先把旧实现装回页面验证其会失败**，否则等同于一个永远通过的空测试。

此外，探针自身也有一个陷阱：`getBoundingClientRect` 是半开区间，鼠标取正好 `b.x+b.w` 的点实际落在元素外，
浏览器不派发 `pointermove`，页面中的 `S.at` 停留在上一位置 —— 探针读到的是过期值（第一版即因此得到错误数据）。
现在贴边取值一律向内让出一个像素，并等待 `S.at` 真正更新后再测量，不依赖 `sleep`。

**10. 光台与放大镜无法同屏：两块各自定尺寸，高度相加超过一屏。**

用户反馈截图显示：滚到光台上能看到框时看不到放大镜，滚到放大镜时又看不到框。先测量：
光台 596 + 间隔 145 + 放大镜 437 = **1178 px**，而可用视口高度仅 **982 px**，相差 196。这 196 px 的来源：

其一，**“结果存哪了”这条提醒横在两块之间**，41 px 的条加上 flex 上下各 22 px 间距，共占 **63 px** ——
它只是一句话，但位置成本远高于观感。它原本挂在光台的下载按钮旁，移到左侧控制台“开始放大”下方更合理：
按下按钮后即在原处告知结果位置，文案中“右边的下载”指的仍是右侧那一栏，表述一致。

其二，其余 133 px 来自两块自身的固定开销：光台长边原按 `56dvh` 计算（596），三格按栏宽计算（277）。
两者各自够大，但没有统一约束总高。现在两个尺寸都由视口高度驱动（光台 `40dvh`、三格 `25dvh`），
系数是解出来的：光台 + 三格 ≤ 视口 − 262（间隔、标题行、取景行、图注、说明为固定开销），
`0.40 + 0.25` 留出的余量恰好使 800 px 高的视口也能同屏。

版式调整容易在“看着对了”时停止，因此 `shots.py` 中增加了 `fit` 断言（光台顶部到放大镜底部这段总高 vs 视口高度），
并按同样规则**先验证其会失败**：临时用行内样式把光台长边改回 `56dvh` 重新测量，断言必须立即报错（差 74 px）。

**11. 双击启动的 `.bat` 不能包含任何非 ASCII 字符，且换行必须是 CRLF。**

两个问题叠加，且都不报错 —— 表现仅为“后面一半命令未执行”。

其一，**cmd.exe 按字节偏移逐行读取 `.bat`**。文件中一旦出现多字节字符，字符数与字节数不再一致，
读取到后面即发生错位：实测报出 `'d'`、`'\pip'` 这类片段，随后按错位的字节继续执行。
最初还有一个诱因是文件被保存为 **LF** 换行 —— 缺少一个 `\r`，cmd 同样会错位。

其二，控制台编码。`.bat` 中的中文 `echo` 在 GBK 代码页下显示为乱码，
而 `server.py` 需要输出的 `✓` `✗` `²` `−` 这几个字符 **GBK 无法表示**。
因此“将控制台切换为 UTF-8”与“`.bat` 保持纯 ASCII”必须同时完成，只做一半仍会有一半是乱码。

现在的分工是：**`.bat` 中不含任何中文字符，只负责找到一个可用的 Python**，
此后所有中文提示均由 Python 输出，通过 `chcp 65001` + `PYTHONIOENCODING=utf-8` 保证显示正常。
提示全部移入 Python 后，三步流程也统一收进 `app/server/bootstrap.py`（失败时暂停等待回车、端口被占用的提示等）——
`.bat` 与 `.sh` 因此都只剩二十余行，两边行为一致，无需分别维护。

两个附带问题：

- `bootstrap.py` 在每次派生子进程前后都强制 `flush`。否则输出被重定向或走管道时，
  父进程与子进程的缓冲各自独立，子进程的输出会插到提示之前，显示为顺序错乱。
- 子进程一律显式设置 `PYTHONIOENCODING=utf-8`。`.sh` 侧没有 `chcp`，
  不显式指定时中文会按系统编码输出而乱码 —— 与 Windows 侧保持一致。

**12. 同参数下输出锐度低于 bigjpg：主因是默认预设的排序。**

用户反馈为“最高参数跟 bigjpg 4x 卡通同一张图，我这边最高都比不过”。
初步判断是参数问题（降噪档、权重族），于是完整扫描了五个预设 × 五档降噪 —— **该假设被否定**：
同参数下锐度均约为 bigjpg 那版的三成，且降噪档越高反而越锐（noise3 的拉普拉斯方差 133 > noise0 的 72），
与“降噪抹平细节”的预期相反。

于是转向模型本身，把每个预设的最高档单独取出、只比较**细节热点区**（眼睛 + 发丝），此时断层清晰可见：
**原生 4× 一次推理的模型可达 bigjpg 的 107%，2× 串联两次的仅 29~37%**。

```
动漫插画 4x-AnimeSharp（原生 4× 一次）   3512  → 107%
通用场景 Real-ESRGAN x4plus              1219  →  37%
卡通/插画 waifu2x CUnet（2× 串联两次）   1133  →  35%
插画高清 waifu2x Swin（2× 串联两次）       936  →  29%
                                          （bigjpg 4x 卡通 = 3279 = 100%）
```

**根因是串联两次会损失细节**，锐化无法弥补。此外还有一处界面问题：最应选的档（4x-AnimeSharp）原本排在**最后**，
名为“动漫线稿”、说明为“线稿专用”，容易被认为与彩色插画无关；而排在**第一位**的恰是最弱的一档。
因此这不是选择错误，而是界面引导错误。

修复分两步：把 `anime` 提到第一位并改名为“动漫插画”、说明改为“彩色二次元插画 / 原画”，
网页与 CLI 的默认预设同步改为它（同时更快 —— waifu2x 系在 DirectML 上数值错误只能跑 CPU，4x-AnimeSharp 可用 GPU）。

**另有一条需要澄清的结论：锐化并非万能。** 曾尝试把增益从 2 提到 6 强行追平 ——
数值上确实达到（锐度 2241 高于 bigjpg 的 2007），但局部对比度为 62.9 而 bigjpg 为 41.3、平块噪声 ×3。
bigjpg 的特征恰恰是**在低对比度下达到高锐度**（41.3 / 2007），这才是有真实细节的表现；
靠拉升对比度得到的高锐度性质不同。**指标可以对上，观感不能** —— 这一点只能通过并排对比图像发现。

两条结论：

- **画质对比不能只调整参数，应先排除“模型逐个单独测试”这一维度。** 同族模型之间的差距可达数倍。
- **界面上排第一的选项即事实上的默认值，它决定使用者得到什么。** 排序不是装饰。

收尾锐化（第 5 步“线条要多清楚”）仍然保留，它解决的是另一个问题 ——
网络输出的边缘天生是渐变的（1 px 的线摊成 4~7 px 灰带），这一步把边缘收回硬边；
平坦区 32×32 块的 std 始终为 `0.00`，不产生噪声。**它的作用是次要的，选对预训练权重才是主要因素。**

**13. 把“绑定地址”当作“可访问地址”使用：服务正常但浏览器无法打开。**

修复前，双击 `start_web.bat` 后窗口内信息一切正常，仅最后一行写着：

```
已经替你打开浏览器： http://0.0.0.0:8765/
```

浏览器中却显示“**嗯…无法访问此页面**”（Chrome 报 `ERR_ADDRESS_INVALID`）。

原因不是端口，也不是服务未启动 —— `0.0.0.0` 是**绑定用的通配地址**，含义为“接收所有网卡的连接”，
这是给 `bind()` 使用的；它本身**并不是可连接的目的地址**，浏览器以它为目标会直接拒绝。
服务自始至终正常（同一进程用 `http://127.0.0.1:8765` 与 `http://192.168.x.x:8765` 均可打开）。

根源是两行代码共用一个变量：`bind()` 使用 `--host`，而**打印与打开浏览器也使用了同一个 `--host`**。
默认 `--host` 为 `0.0.0.0`（为了让手机也能连接），于是该字符串被原样拼进了 URL。

修法是**把两件事分开计算**：绑定位置是一回事，可访问地址是另一回事。
通配地址一律对外报告 `127.0.0.1`，绑定所有网卡时**再附一条局域网地址**（绑定 `0.0.0.0` 的用途
本就是让其他设备连接，因此直接把应输入的地址给出）。同时把“已启动”的打印移到 `bind()` **之后** ——
端口被占用时先打印一行“已启动”再报错，那行错误信息最容易造成误导。

**此外还发现第二个问题：局域网地址最初输出错误。** 查找本机内网 IP 的常规做法是
“UDP `connect` 一个外网地址，观察内核选择了哪张网卡” —— 在本机上该方法每次都返回
**`198.18.0.1`**。该地址属于 `198.18.0.0/15`，即 RFC 2544 性能测试网段，被代理软件的 TUN 网卡占用，
且**默认路由位于该网卡**，因此内核选中的就是它。这不是内网地址，其他设备无法连接 ——
相当于把“浏览器打不开”换成了“手机打不开”。改为枚举所有网卡 + 探针兜底，并过滤
回环 / 链路本地 / 这几个虚拟网段（`192.168` 优先，其次 `10.x`、`172.16/12`），现在输出为 `10.103.89.173`。

**还有一层：该功能异常不得影响启动。** 过滤网段的字符串最初写成 `198.19.0.0/15`
（`ipaddress` 判定其 host bits set，不合法），而它会在启动横幅中被调用 ——
一旦触发即为“双击启动闪一下就退出”。因此外层增加降级处理：探测失败时只是不输出该行提示。
同时让 `smoke.py` 直接测试真实实现（并额外模拟一次异常，确认降级路径确实可达，
而不是一个永远不会执行的 `except`）—— **错误应在自检中暴露，不应留给使用者去触发。**

**顺此线索还发现另一件事：Windows 上“端口被占用”不会报错。**
`http.server` 默认 `allow_reuse_address=1`，Windows 的 `SO_REUSEADDR` 语义允许
**第二个进程绑定同一端口**（Linux 会直接拒绝）。因此旧窗口仍打开时再启动一个，
两边都打印“已启动”，而请求只会发送到后启动的那个 —— 使用者看到的则是“代码修改未生效”。
现在启动时先实际连接一次该端口（处于 `TIME_WAIT` 的旧 socket 不会 accept，因此正常重启不会误报），
探测到已有服务在运行即给出提示。

结论：**不应将“可监听的地址”与“可访问的地址”视为同一事物**，`0.0.0.0` 与 `::` 都属于前者；
**“本机内网 IP”也不是可以随意获取的信息**，配置了代理 / VPN 的机器上尤其需要注意。
这也是“自检全绿但实际使用即失败”的典型案例 —— 验收时始终显式添加
`--host 127.0.0.1`，恰好绕开了双击启动那条路径。

**14. 隐藏元素需要同时移出视口并从可访问性树中移除。**

窄屏控制栏改为从底部拉起的抽屉，收起时整块 `translateY(101%)` 移出视口。

截图上它确实不可见，但它**仍在页面上**：键盘 Tab 仍可进入，进入后焦点落在
被遮罩覆盖、且位于视口外的区域。用户按 Tab 只能看到焦点消失，容易误判为页面卡死。
修法是同时设置 `visibility:hidden`（配 `transition:visibility 0s .28s`，
待滑出动画结束后再隐藏，否则会看到它中途突然消失）。

这一条单独记录，是因为它属于**“看不出异常”的类型**：截图正常、像素对比正常、
“页面无 JS 报错”也正常，只有实际按 Tab 才会发现。因此 `shots.py` 现在**同时测量两项** ——
位置（`top` 是否确实在视口下方）与 `visibility` 是否为 `hidden`。
只测量位置的话，仍留在可访问性树中的抽屉也能通过检查。

同一批修改中还发现一个较小的问题：页脚的折叠控件三角在窄屏下消失。原因是为把点击区抬到 44 px，
`summary` 被改为 `display:flex` —— 而 Chrome 中 `display:flex` 的 `summary` **不会绘制 marker**，
于是“两个必须说清的坑”看起来像普通正文，无法辨识其可点击。补一个由 `::before` 绘制的三角即可
（`.adv` 那一栏本就是这种做法）。

## 关于“无损”

严格来说超分不可能无损 —— 小图中不存在的像素，大图必须补出。模型做的是“低损 + 符合视觉预期”：
它依据训练中习得的经验补出边缘与纹理。**照片、文字、细密网格这类高频内容缺乏可靠先验，模型会编造出不存在的细节。**
不建议用于还原监控截图中的车牌或文件中的文字。
